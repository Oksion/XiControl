# IoT-модуль удалённого включения (Xiaomi remote wake) — разбор и вывод

Восстановлено из: реверс OEM-стека `XiaomiRemoteDesktop 5.8.0.17` + `XiaomiPCManager 5.8.0.74`
(декомпиляция .NET через `ilspycmd`, дизасм нативного через rizin) + **живые пробы на TM2424
2026-07-28** (IPC-канал, miIO по LAN, HTTP к облаку). Драйверы OEM лежали локально в
`Driver/IOT` (в репозиторий не входят).

> **TL;DR.** У ноутбука есть **отдельный always-on IoT-модуль** (второй Wi-Fi-чип), который
> может включать ПК из полностью выключенного состояния по команде из облака Xiaomi. Мы полностью
> вскрыли его локальный протокол и **завели модуль в домашнюю сеть без всякого аккаунта**. Но
> удалённое включение работает **только через китайское облако Xiaomi**, вход в которое
> заблокирован на трёх уровнях (нет международного бэкенда → `502`; нужен CN-аккаунт; нужна
> привязка в Mi Home), а всё в итоге упирается в 128-битный miIO-токен, доступный лишь из облака
> или дампа флеша. **Фичу driver-free сделать нельзя. Не берём** (как TDP и NFC). Документ — чтобы
> не ходить по этому кругу заново.

---

## 1. Что это за железо

| Параметр | Значение |
|----------|----------|
| ACPI HWID | `ACPI\IOTD0000` («Xiaomi IoT Module») |
| Драйвер | `IoTDriver.sys` (KMDF) + служба `IoTService.exe` (авто-старт `IoTSvc`) |
| Модель (miIO) | `xiaomi.laptop.p52` (для TM2424) |
| DID (device id) | уникален для каждого экземпляра модуля |
| Прошивка модуля | формат `1.0.x_00xx` |
| Радио | отдельный **2.4 ГГц** Wi-Fi, живёт при выключенном ПК |
| Пробуждение ПК | модуль будит хост через EC по облачной команде |

Модуль — самостоятельное устройство экосистемы Mi IoT (米家): держит собственное Wi-Fi-соединение,
сам ходит в облако Xiaomi, а разбуженный по DID через miIO/MIoT поднимает ноутбук. Служба ↔ драйвер
общаются по IOCTL, драйвер ↔ модуль — по **RAM-мейлбоксу** (`RamDevice::Read/Write`, `cmd %02X → ack → ret`).

Соседние папки драйверов к пробуждению **не относятся**: `Intel_PTL_ISH` = presence-сенсор,
`MEP` = Windows Studio Effects (камера/NPU), `NFC` = NTAG5 (см. память проекта, NFC в Windows не выведен).

## 2. Локальный канал управления модулем (вскрыт полностью)

OEM тащит с собой `IotIPCManager.dll` — готовый C-API ко всему модулю. Транспорт —
**JSON поверх named pipe** `\\.\pipe\LOCAL\IoTService_IPC_Broker`. Точные сигнатуры взяты из
декомпиляции `XiaomiRemoteDesktop.exe` (`IoTConfig/DllImports.cs`; сами `Iot*.dll` нативные, cdecl).

### Экспорты `IotIPCManager.dll`

| Функция | Назначение |
|---------|------------|
| `IPC_Init(logPath)` / `IPC_Uninit()` | подключиться/отключиться от брокера |
| `IPC_GetDeviceStatus(out s)` / `IPC_SetDeviceStatus(s)` | питание/готовность модуля (1=вкл, 0=выкл) |
| `IPC_GetModel(buf)` | `xiaomi.laptop.p52` |
| `IPC_GetFirmwareVersion(buf)` | версия прошивки |
| `IPC_GetDeviceID(out did)` | DID модуля |
| `IPC_GetBindStatus(out bound, out uid)` / `IPC_BroadcastSetBindStatus()` | привязка к UID Mi-аккаунта |
| `IPC_WriteWiFiItem(ssid, pass, connectNow)` | **залить модулю Wi-Fi** |
| `IPC_ConnectWiFi()` / `IPC_ReadWiFiStatus` / `IPC_ReadWiFiCount` / `IPC_GetWiFiByIndex` | управление/чтение сетей |
| `IPC_DeleteWiFiItem(ssid)` / `IPC_EmptyWiFiItems()` | **забыть Wi-Fi** (одну / все) |
| `IPC_ResetDevice()` | сброс модуля |
| `IPC_SendLaptopStatus(s)` | сообщить модулю состояние ноутбука |
| `IPC_Register{Bind,WiFi}StatusCallback` | подписка на события |

### Формат обмена (из живого лога `IotIpcConfig.log`)

```
SrcId=0x0001 (клиент) → DstId=0x0002 (служба),  Type=<код>,  Data={"Data":{…},"ErrCode":0,"ErrorMsg":"…"}
```
Типы сообщений: `101` GetDeviceStatus, `102` SetDeviceStatus, `103` FwVersion, `104` BindStatus,
`110` ReadWiFiStatus, `111` ReadWiFiCount, `113` GetModel, `115` GetDeviceID;
события `10001` BindStatusChange, `10002` WiFiStatusChange.

Статусы Wi-Fi (`IPC_ReadWiFiStatus`): `1` CannotConfigOver30Min, `2` WaitingConfigInBroadcast,
`3` NotConnected, `4` ConnectedToNetwork, `5` ConnectedToCloud, `6` OtaInProgress, `7` WiFiClosed.

### ⚠️ Две ловушки (обе стоили времени)

1. **Слот клиента у брокера.** Ответы адресуются одному клиенту (`DstId=0x0002`). Пока запущен сам
   `XiaomiRemoteDesktop.exe`, свой клиент получает `IPC_Init=0`, но **все вызовы возвращают `-2` (timeout)**.
   Лечится закрытием OEM-приложения. Права администратора для IPC **не нужны** (в отличие от MIFS).
2. **30-минутное окно настройки.** Модуль принимает Wi-Fi **только 30 минут после подачи питания**,
   иначе `ReadWiFiStatus = 1 (CannotConfigOver30Min)` и запись молча не проходит. Окно
   переоткрывается циклом питания: `SetDeviceStatus(0)` → пауза → `SetDeviceStatus(1)` → статус `2`.

## 3. Живой результат на TM2424 (2026-07-28)

- Прочитаны `Model / DID / Firmware / BindStatus` через IPC; DID совпал с miIO-hello по LAN.
- **`WriteWiFiItem(SSID, pass, connectNow=1)` завёл модуль в домашнюю сеть:**
  `2 WaitingConfig → 3 NotConnected → 4 ConnectedToNetwork → 5 ConnectedToCloud`.
- **Аккаунт Xiaomi для этого не нужен вообще** — `BindStatus=false, UID=0` на всех этапах.
- Модуль только 2.4 ГГц; совмещённый SSID (2.4+5) подходит. Пароль берётся локально из профиля
  Windows: `netsh wlan export profile key=clear` → `<keyMaterial>` (в логи/вывод не попадает).

## 4. miIO по LAN — и стена токена

После провижининга модуль поднялся **отдельным IP** и отвечает на miIO-hello (UDP `54321`, magic
`21 31`, 32 байта): вернул свой DID (совпал с прочитанным по IPC), растущий `stamp`, но **токен скрыт
(`ff`×16)**.

- miIO-команды шифруются AES-128-CBC: `key = MD5(token)`, `iv = MD5(key+token)`. Токен — 128-битный
  секрет, перебор бессмысленен.
- Токена **нет** ни в `IoTService.exe`, ни в `IoTDriver.sys`, ни в `IotIPCManager.dll` — Xiaomi
  отдаёт его только телефону через облако.
- Порт-скан модуля: открыт **только `54321/udp`**, ни HTTP, ни mDNS, ни SSDP, своей точки доступа не
  поднимает. Наружу токен не выставляется ни при каких условиях.

→ Локальное управление модулем без токена закрыто. Токен добывается лишь из **облака** (нужен
аккаунт) или **дампа флеша** (UART/SPI — отдельный, «железный» заход).

## 5. Почему облачный путь закрыт (`502 Bad Gateway`)

OEM-приложение при логине зовёт `GET https://remotecontrol.xiaomi.com/api/account/` и
`/pass/serviceLogin?sid=remotecontrol` → **`502` от самого шлюза Xiaomi** (`Server: MiFE/3.4.29`,
openresty; WebView получает HTML вместо JSON). Разбор:

- `remotecontrol.xiaomi.com` CNAME → `mife-pub-stable-**azams**.alb.xiaomi.com` → Azure **Amsterdam**.
  Не-Китай GSLB Xiaomi заворачивает всех на **европейский** edge.
- Edge жив, DNS резолвится, TLS встаёт — но **за международным edge нет бэкенда `remotecontrol`**
  (сервис развёрнут только в китайском регионе). Отсюда `502`.
- **Доказательство:** OTA-хост `whippet.bsp.xiaomi.com` идёт через **тот же** azams-edge и **работает**
  (`{"code":0,"message":"ok"}`). Значит дело не в сети и не в блокировке — именно у удалённого
  управления нет международного деплоя. И китайский DNS (AliDNS/DNSPod) при запросе с нашего IP отдаёт
  тот же azams — хост гео-роутится по egress.

Эндпоинты (`XiaomiRemoteDesktop.Utils/GlobalVariables.cs`): `ServerUrl=remotecontrol.xiaomi.com`,
`ssoHost=account.xiaomi.com`, OTA=`whippet.bsp.xiaomi.com`, `ClientID=2882303761520281327`.

**Вывод про VPN.** Китайский выход убрал бы **именно** `502` (дошёл бы до CN-edge с живым бэкендом),
но это лишь **первый из трёх замков**: дальше нужен аккаунт региона «Материковый Китай» + привязка в
Mi Home (которая у самого модуля тоже идёт через облако), и всё равно упираешься в токен.
Международной версии фичи **не существует** (XDA / xiaomi.eu / 知乎: Hyperconnect/远程控制 привязаны к
Xiaomi-ноутам + региону CN/EU-ROM; патчами снимают только ограничение по модели железа, не регион
бэкенда). Официальный путь remote-wake: привязка в Mi Home App → апдейт прошивки модуля через
Mi Home — оба шага через китайское облако.

## 6. Связь с MIFS `0x0C` (уточнение к [01-wmi-protocol.md](01-wmi-protocol.md))

`DeviceStatus` модуля дублируется **и в MIFS** (driver-free WMI, без OEM-софта, но нужен админ):
RE `IoTService.exe` показал `getDeviceStatus` = `IN[1]=0xFA IN[3]=0x0C IN[4]=0x03`,
`setDeviceStatus` = `IN[1]=0xFB … IN[6]=<val>`; значение в `OUT[6]`, статус `OUT[1]=0x80`.

Это **переопределяет** прежнюю догадку в доке 01 (что `0x0C` — рудиментный слот TPLock из общей
кодовой базы): на самом деле `0x0C` — **канал питания/статуса IoT-модуля**. Живые дельты подфункций
(elevated GET): `0x0C/0x02 = 1` статично («модуль присутствует»); `0x0C/0x06` флипнулся `0→1` после
установки OEM-софта и входа в Mi-аккаунт («привязан / remote-wake активен»); `0x0C/0x03` — питание.

**★ Питание пишется, не только читается (подтверждено 29.07.2026):** `SET 0xFB 0x0C 0x03 0/1`
**реально гасит/будит модуль**, а не просто хранит флаг — проверено: после `SET=0` модуль уходит в
offline и **держится** (пока его не включит обратно служба `IoTSvc`, см. §8). Это тот же путь, которым
OEM-служба делает `SetDeviceStatus`. Значит **вкл/выкл питания модуля XiControl может делать driver-free,
своим MIFS-каналом** — без OEM-DLL. А вот Wi-Fi-провижининг, DID и сама команда пробуждения в MIFS
отсутствуют — только через OEM-пайп/облако.

## 7. Вывод для XiControl — 🚫 не берём

Удалённое включение из выключенного состояния через этот модуль **несовместимо с проектом сразу по
двум осям**:

1. **Технически недостижимо.** Реальная команда wake живёт в китайском облаке по DID и требует
   miIO-токена, которого у нас нет и легально не будет (см. §4–5). Даже локальный канал провижининга
   (§2) — это **OEM-служба + named pipe + нативная DLL**, ровно то, от чего проект отказывается.
2. **Смысла нет.** В обмен на постоянную связь с китайскими серверами модуль не даёт driver-free
   функционала.

Поэтому **удалённое включение в код не идёт — вопрос закрыт.**

Но есть обратная, полезная сторона: **выключить модуль** (чтобы он не включался сам и не висел в
эфире) — делается **driver-free**: питание через MIFS `0x0C/0x03` (§6) + отключение службы-«будильника»
`IoTSvc` (§8). Это реальный кандидат в фичу — тумблер «Выключить IoT-модуль» по паттерну явного opt-in,
как `ApiFirewall`/`AutoStart` (XiControl уже делает системные действия по явному клику). **Пока в код не
берём — по решению, есть более приоритетные задачи**; процедура задокументирована в §8 как ручная. Если
руки дойдут — переносим из «не берём» в работу.

> Родственные закрытые вопросы: TDP в ваттах и NFC — [05-open-questions.md](05-open-questions.md),
> раздел «🚫 Не берём» в [../ROADMAP.md](../ROADMAP.md).

## 8. Как заглушить модуль (приватность)

Раз функционала нет, а связь с облаком есть — модуль надо заставить **не доходить до облака**.
Всё — тем же локальным IPC, обратимо. OEM-приложение `XiaomiRemoteDesktop.exe` предварительно
закрыть, иначе IPC таймаутит (ловушка №1).

### ⚠️ Что НЕ работает (проверено на TM2424 2026-07-28)

Сохранённая (активная) сеть сидит в NVRAM модуля **глубже, чем достаёт IPC-«забывание»**:

- `IPC_EmptyWiFiItems()` → возвращает `0`, но после цикла питания модуль **снова уходит в
  `ConnectedToCloud`** к старой сети.
- `IPC_DeleteWiFiItem(ssid)` → `-5` (ошибка), сеть остаётся.
- `IPC_ResetDevice()` → возвращает `0`, но **тоже не стирает** активную сеть (переподключается).

Похоже, эти вызовы чистят некий «список кандидатов», а активная сеть хранится отдельно и через IPC
не удаляется.

### ✅ Что работает — перезапись на сеть-призрак

`IPC_WriteWiFiItem` во флеш **пишет** (это и доказал факт переподключения после нашего провижининга).
Поэтому вместо стирания — **перезаписать активную сеть на несуществующую**:

1. Открыть 30-мин окно: `SetDeviceStatus(0)` → пауза → `SetDeviceStatus(1)` → дождаться статуса `2`.
2. `IPC_WriteWiFiItem("XIControl-blocked-do-not-connect", "<мусор>", connectNow=1)`.
3. Проверить циклом питания: модуль держит фиктивный SSID, **до `ConnectedToCloud` не доходит**, и
   старая сеть **не всплывает** (перезапись её вытеснила).
4. `IPC_SetDeviceStatus(0)` — обесточить.

Результат: даже если OEM-служба включит модуль на следующей загрузке, он тыкается в сеть-призрак и в
облако не ходит. Готовые скрипты — в локальном `reference/` (в репозиторий не входят, дёргают OEM-DLL).
Возврат — `WriteWiFiItem(...)` с реальной сетью.

### ★ Самое чистое и durable — отключить службу `IoTSvc` (проверено 29.07.2026)

Кто именно включает модуль обратно — выяснено: **служба `IoTSvc`** (её exe лежит в
`C:\WINDOWS\System32\DriverStore\FileRepository\iotdriver.inf_*\IoTService.exe` — ставится с
`IoTDriver.inf`, т.е. это часть **драйвера устройства**, а НЕ приложения; снос `XiaomiRemoteDesktop`
её не трогает). Именно она делает `SetDeviceStatus(1)` на старте — вот источник «модуль сам включается».
Отсюда чистый, полностью обратимый рецепт **без OEM-DLL**:

1. `Set-Service IoTSvc -StartupType Disabled; Stop-Service IoTSvc -Force` — убрать «будильник».
2. Погасить модуль нашим MIFS-каналом: `SET 0xFB 0x0C 0x03 0` (см. §6).

**Готовый скрипт — [`tools/Disable-IoTModule.ps1`](../tools/Disable-IoTModule.ps1)** (`-Action Disable` /
`Enable` / `Status`): делает ровно эти два шага, сам поднимает UAC, driver-free (MIFS + служба, без
OEM-DLL), полностью обратим. **Проверено:** после `Disable` питание модуля = `0` и **держится** (через
20с без службы всё ещё выкл — включать некому). `XiaomiPCManager` к модулю ходит только через `IoTSvc`,
так что при отключённой службе безопасен. Откат — `-Action Enable`.

Это закрывает и приватность (модуль не в сети), и «само включается» (служба не стартует). Перезапись
Wi-Fi на сеть-призрак (выше) остаётся «поясом»: даже если модуль как-то окажется включён, в облако он
не дойдёт.

> 🔒 **Ещё варианты:** MAC-блок модуля на роутере (виден отдельным клиентом сети) или полный снос
> OEM-стека (`XiaomiRemoteDesktop` + PC Manager) — фича всё равно мёртвая.
