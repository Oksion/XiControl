# Проверка драйверов и BIOS у OEM

Как Xiaomi проверяет обновления драйверов и прошивок для ноутбука — протокол, разобранный
до состояния «можно повторить без их софта». Нужен, если мы захотим показывать такую проверку
в XiControl: канал driver-free, обычный HTTPS плюс WMI, ни драйверов, ни служб Xiaomi не требуется.

Разбор снят 2026-10-10 на Xiaomi Book Pro 14 (TM2424): Xiaomi PC Manager 5.8.0.57 +
служба MiService 4.1.1.564. Сырые данные захвата — в `ota-capture/` (вне репозитория,
см. [«Где лежат данные»](#5-где-лежат-данные)).

---

## 1. Кто за что отвечает

| Компонент | Роль |
|---|---|
| Xiaomi PC Manager (`SvrCModule.dll`) | **только UI**. `sc::DriverManagerModule` / `DriverClientManager` гонят protobuf `xsa.*` (`StartScanDriver`, `GetDriversDetail`, `InstallDriver`) по named pipe. Сам в сеть за драйверами не ходит |
| **MiService / MiDeviceService** (`MiDeviceServiceEntry.dll`) | **бэкенд**: `driver::ScanTask` (включая `ScanFirmware` и «scan bios»), `driver::GetDriverInfoFromServerOTA`, `OTA::UpdateStrategyManagerImpl::ConstructPostData`, `firmware::GetFirmwareInfos`. Живёт и после удаления PC Manager |
| `FirmwareScreenTool.exe` | версия прошивки TCON панели (Himax HX8874) через `IGCLCSharpDLL.dll` → IGCL `ctlAUXAccess`, пишет её в реестр; разбор — §4, XIC-103 |

То есть сетевая часть целиком в службе. PC Manager нужен лишь чтобы нажать «проверить».
Что ещё делают эти службы, чем мешают XiControl и как их отключить — [17-oem-services.md](17-oem-services.md).

## 2. Запрос

Один запрос на **один** модуль; полный скан = 26 запросов.

```
POST https://whippet.bsp.xiaomi.com/api/v2/nb/checkUpdate
Content-Type: application/x-www-form-urlencoded
User-Agent: mi-service

data="<base64(root)>"
```

```jsonc
// root
{"body":{…},"header":{"appid":"nb-DBRUc9Fdui","sign":"<MD5(appid+body+key), ВЕРХНИЙ регистр>"}}

// body — ключи строго по алфавиту, компактный JSON без пробелов
{"category":"driver","lan":"ru_RU","modules":[{"moduleName":"NPU"}],
 "product":"TM2424","region":"RU","sn":"77079/6d4fe817…","winBuildNumber":"26200"}
```

Порядок ключей не случайный: тело собирается `nlohmann::json` на `std::map`, то есть всегда
по алфавиту. Любое отступление ломает подпись.

### Поля

| Поле | Откуда берётся | Примечание |
|---|---|---|
| `category` | `"driver"` | **для всех модулей, включая прошивки** (`FWTP`, `FWSC`). Отдельно идёт один запрос с `"bios"` |
| `modules` | `[{"moduleName":"<код>"}]` | **без `version`**: спрашивается «какая последняя», установленная версия серверу не сообщается. Исключение — `category: bios` |
| `product` | реестр `HKLM\SOFTWARE\MI\MiDeviceService\ProductModel` (= `Win32_BaseBoard.Product`) | `TM2424`. **Не** SKU `TM2424-77079` и не `77079` |
| `sn` | `<часть1>/<md5_lower(весь IdentifyingNumber)>` | `IdentifyingNumber` = `77079/26S400093` → `77079/6d4fe817…`. **Настоящий серийник не передаётся**, только хеш. Поле необязательное: без него ответ тот же |
| `lan` / `region` | системная локаль (`GetUserDefaultUILanguage` + `GetLocaleInfoEx`) | на `ru_RU` / `RU` сервер работает нормально — региональной блокировки нет |
| `winBuildNumber` | билд Windows | `26200` |

Подпись: `MD5(appid + body + key)`, верхний регистр. `appid` = `nb-DBRUc9Fdui`,
ключ = `OH3QAmMrso1DhOm4` — оба зашиты в `MiDeviceServiceEntry.dll`.
Есть и моки для отладки: `HKLM\SOFTWARE\MI\Driver` → `MockUrl` / `MockAppId` / `MockAppkey` / `MockProduct`
(на штатной машине пусто). Staging-адрес в бинаре: `matrix.whippet-updater.staging.mi.com`.

### Коды модулей

Драйверы: `WLC WC IGC IDC SC BT FR TBT ISH GNA HID CG ME SIO HR RST NPU MEP PMT HDR NFC OTS`.
Прошивки: `BIOS`, `FWTP` (тачпад), `FWSC` (экран).

### Отдельная ветка BIOS

Единственный запрос, который несёт версию:

```jsonc
{"category":"bios","modules":[{"moduleName":"BIOS","version":"1.0.0.2570"}], …}
```

Версия кодируется хитро: `1.0.0.` + **десятичное от последних четырёх hex-символов**
`Win32_BIOS.SMBIOSBIOSVersion`. Формат `1.0.0.%04d` зашит в бинаре.

```
XMAPT4B0P0A0A → "0A0A" → 0x0A0A = 2570 → "1.0.0.2570"
```

## 3. Ответ

```jsonc
{"code":0,"message":"ok","traceId":"…","modules":[{
  "product":"TM2424","category":"driver","moduleName":"NPU",
  "latestVer":{
    "version":"NS","versionSerial":1788165356520,"displayVersion":"N.S","logInfo":{},
    "packages":[{"type":"FULL_PACKAGE","md5":"9e6fc14c…","fileSize":35632547,
                 "fileName":"MO3n_08.Intel_PTL_NPU_32.0.100.4841.zip",
                 "mirrors":["https://cdn.cnbj1.fds.api.mi-img.com/ota-packages/…zip"]}],
    "strategy":{"upgradeChannel":"MISERVICE","powerRequireSw":0,"manualUpgrade":0,"newInstall":0,
                "hardwareIds":[{"id":"PCI\\VEN_8086&DEV_B03E","releaseTime":"2026-07-24",
                                "version":"32.0.100.4841"}],
                "installScripts":[{"pt":"win11","path":"08.Intel_…/install.bat"}],
                "autoRestart":0,"autoExceptionCheck":0,"autoUpdate":0}}}]}
```

Важные грабли:

- **Настоящая версия — в `strategy.hardwareIds[].version`.** Поле `latestVer.version` всегда
  заглушка `"NS"`, `displayVersion` — `"N.S"`.
- **Один пакет — много версий.** Внутри `hardwareIds` версии **разные**: у аудио (`SC`) 125
  hardware-id и 10 различных версий (архив везёт Intel SST, Realtek и Dolby, у каждого своя),
  у графики — 59 id и 6 версий. Поэтому «версии пакета» не существует: сравнивать можно только
  попарно, наш hardware-id → его запись в каталоге.
- `modules: []` означает «для этого типа на эту модель пакета нет», а **не** «нет обновлений».
  На захваченном скане пакет пришёл в 17 ответах из 26.
- Ошибки сервера: неверная подпись → `{"code":500,"message":"签名校验失败"}`;
  пустой `data` → `{"code":500,"message":"服务未注册"}`.
- **`category:"application"` не существует.** С ней сервер отвечает `code:0 ok` и пустым
  `modules` — молча, без ошибки. На эту ловушку легко потратить часы.

### Как из ответов получается каталог

Служба склеивает `hardwareIds` × пакет в плоскую карту `{hardware_id → пакет}` и кладёт в
`…\MiService\<ver>\MiDeviceService\driver_cache.dat`. Отсюда 1259 hardware-id при 18 пакетах:
один zip закрывает десятки ревизий и конфигураций одной модели.

## 4. Что из этого можно сделать у нас

> **Сделано в XiControl (XIC-95):** вкладка «Настройки → Драйверы». Запрос — только по кнопке,
> без `sn`, со своим User-Agent `XiControl-driver-check` (сервер его принимает, выдавать себя за
> `mi-service` не нужно); 24 модуля + BIOS параллельно по 4, полный скан на TM2424 — ~4 с. Код —
> `src/SystemIntegration/OemDrivers.cs`: `OemProtocol` (тело, подпись, разбор — подпись сверена с
> захватом службы до символа), `DriverMatch` (сверка попарно по hardware-id), `OemDriverCheck`.
> Показываем сводку по модулям и подробно — только обновления, со ссылкой на пакет (второе нажатие
> открывает её в браузере). У BIOS — тоже ссылка, но под отдельным предупреждением «на свой страх
> и риск» (решение владельца: иначе родная утилита оставалась бы нужна ради одного BIOS). Ничего не
> скачиваем и не ставим.
>
> **Прошивки `FWTP`/`FWSC` (XIC-102)** — отдельная группа «Прошивки», по строке на модуль, если сервер
> вернул пакет: «Прошивка: Тачпад / Экран — в каталоге версия X», ссылка на пакет под предупреждением
> как у BIOS. Сверки по hardware-id для них **нет**: их id в каталоге синтетические
> (`USB\VID_6789&PID_1234&REV_1236/1237` у экрана, `USB\VID_6989&PID_1234&REV_1836/1837` у тачпада) и в
> `Win32_PnPSignedDriver` не встречаются — до XIC-102 строка была недостижима, и XiControl молчал там,
> где PC Manager предлагал прошивку. Версия — из `hardwareIds[0].version` (на TM2424: `740B08` у экрана,
> `3.5.13.01.44.25.13.0` у тачпада), имя устройства — локализованная константа по коду модуля, не из PnP.
> С версией драйвера не сравниваем. Текущую версию прошивки с XIC-104 читаем сами (ниже). Для обычных
> драйверов правило прежнее: нет совпавшего устройства — нет строки.
>
> **Сверка модели в ответе (XIC-103).** Каждый модуль ответа несёт поле `product`. Модуль, где сервер
> явно назвал не ту модель, о которой спрашивали, отбрасывается (`OemProtocol.ParseResponse`, без учёта
> регистра; модуль без поля остаётся — доказать «чужую модель» нечем). Для драйверов это страховка поверх
> сверки по hardware-id, для прошивок — **единственная** проверка, что пакет про этот ноутбук.
>
> **Текущая версия прошивки (XIC-104)** — по разбору ниже, только для модулей, на которые в каталоге
> есть пакет, по кнопке проверки, на пуле (`OemDriverCheck.RunAsync(currentFirmware)` →
> `DriverMatch.Compare(..., firmware)`):
>
> - **тачпад** — две прошивки, обе читаются: контроллер касаний BL7853 —
>   `TouchpadHaptics.ReadControllerVersion()` через `COL04`, MCU силы и вибрации —
>   `ReadFirmwareVersion()`, команда `0x10` канала `COL05` (разбор — `TouchpadHapticsProtocol`).
>   Каталожная версия делится на части (`DriverMatch.TouchpadCatalogParts`: `3.5.13.01.44.25.13.0` →
>   `3.5.13.1` + `44.25.13.0`), текущая собирается так же (`TouchpadCurrent`, «контроллер / сила»), и
>   строка получает обычное «обновление / актуальна / новее каталога»: обновление — если старее хоть
>   одна часть. Не ответил `COL04` — сравниваем одну силу, без силы — «версия неизвестна». На TM2424
>   живьём: установлено `3.5.9.1 / 44.25.11.0`, в каталоге `3.5.13.1 / 44.25.13.0` → «обновление»;
> - **экран** — `PanelFirmware.ReadRomVersion()`, ROM Ver контроллера Himax через IGCL; чистая часть
>   (последовательность операций, раскладка `ctl_aux_access_args_t`, разбор ответа) —
>   `PanelFirmwareProtocol`, тесты сверяют записи с OEM байт в байт. Версия в формате каталога
>   (`570B06`) показывается **рядом** с каталожной, состояние остаётся «сравнить нельзя» — см. «Чего это
>   не решает». Своя инициализация IGCL на один вызов, записи — только на выходе, где DPCD `0x400`
>   ответил OUI Himax; первая неудачная операция обрывает последовательность;
> - не прочиталось → «версия неизвестна, в каталоге X» (у экрана — с подсказкой про локальный сеанс).
>   Результат каждого чтения пишется в журнал (`OemDriverCheck: текущая прошивка FWTP — …`).

Сверка «что установлено против того, что есть у OEM» делается без сети и без Xiaomi-софта:

1. Берём каталог — из ответа сервера (запрос выше) или из `driver_cache.dat`, если служба стоит.
2. Перечисляем установленное через `Win32_PnPSignedDriver` (`HardwareID` + `CompatID`).
3. Сопоставляем: **hardware-id каталога — префикс установленного id**
   (`ACPI\INTC105F` ⊂ `ACPI\INTC105F&…`), и версию берём **из записи этого же hardware-id**,
   а не «пакета» (см. выше: в одном пакете версии разные).
4. Текущий BIOS — `Win32_BIOS.SMBIOSBIOSVersion`, сравнивать строкой.

Проверено на железе: живой запрос по модулям WLC/IGC/SC/CG вернул каталог, сверка дала осмысленную
картину — у аудио и чипсета всё совпало до версии, по графике и Wi-Fi установлено новее каталога.

**Загрузка работает** (проверено на самом маленьком пакете, 27 326 байт): прямой GET по
`mirrors[0]`, без авторизации и токенов, размер и `md5` из каталога совпали. Зеркало ровно одно.

Установка — сознательно **не делаем**: это запуск их `install.bat` от администратора. Любопытно,
что сам батник — лишь обёртка (`DeviceCheck.exe` по hardware-id, затем
`pnputil /add-driver <inf> /install`), то есть при желании обошлись бы штатным механизмом Windows
без их скрипта. Но проверен ровно один, простейший пакет; аудио и графика почти наверняка гонят
вендорский `setup.exe`. BIOS тем более не ставим сами — только ссылка с предупреждением.

**Ограничения:**

- каталог живёт у них на сервере и устаревает в кэше: полагаться только на локальный
  `driver_cache.dat` нельзя — он даст «всё актуально» там, где это уже не так;
- метаданные местами мусорные (у чипсета `releaseTime` = `1968-07-18`) — даты показывать с оглядкой;
- **текущая версия прошивки** читается driver-free (XIC-103, XIC-104), но «у вас старее» говорим только
  про тачпад; у экрана — обе версии рядом, и только когда панель активна;
- hardware-id прошивок в каталоге **синтетические** и ни с чем в системе не совпадают — сверять их
  по PnP бессмысленно, строка даётся по факту пакета для модели.

### Текущие версии прошивок (ресерч XIC-103)

**Тачпад (`FWTP`) — читается, стабильно.** Команда `0x10` нашего канала `COL05` (тот же, что у
тактильного отклика XIC-77, без повышения прав): ответ `2C 19 0B 00` = **44.25.11.0**. Работает и по
RDP — HID-устройство от сеанса не зависит. В каталоге `3.5.13.01.44.25.13.0` — **две** прошивки
(см. «Что внутри пакета тачпада» ниже): `3.5.13.01` — контроллер касаний BL7853, `44.25.13.0` —
MCU силы и вибрации. Команда `0x10` отдаёт версию второго: на TM2424 стоит 44.25.11.0, старее
каталожной. Служба Xiaomi FWTP не видит вовсе: ищет версию в реестре и пишет «Failed to get current
firmware version for FWTP».

**Контроллер касаний BL7853 — через `COL04` (XIC-104).** Канал `0xFF00`, Report ID `0x0E`, 33 байта.
Первым запрос опубликовал gxcreator в [issue #99](https://github.com/Oksion/XiControl/issues/99); мы
сверили его с кодом `FirmwareTouchPadTool.exe` из пакета (запись кадра по смещению файла `0x1C7EA`):

- запрос — константный кадр `0E 07 B4 00 00 01 00 04 B6` + нули до 33 байт, `HidD_SetOutputReport`;
- пауза **30 мс**, затем `HidD_GetInputReport` с `[0] = 0x0E`;
- годен ответ с `[1] = 0x06` и `[2] = 0xB6` (эхо команды, суммы в этом канале нет), версия —
  байты `[7].[6].[4].[5]` десятичными.

Это **единственный** кадр, который XiControl шлёт в `COL04`, и он не собирается, а взят как есть.
На TM2424: **3.5.9.1** при `3.5.13.01` в каталоге; у автора #99 после прошивки — 3.5.13.1 и 44.25.13.0.

**Экран (`FWSC`) — читается, но нестабильно и не без записи.** Это прошивка **TCON-контроллера
панели Himax HX8874**, а не «монитора». `FirmwareScreenTool.exe --version` (так его зовёт служба,
потом пишет волатильный `HKLM\SOFTWARE\MI\Driver\Firmware\TouchPanelVerion`) ходит через свою
обёртку `IGCLCSharpDLL.dll` в Intel IGCL `ctlAUXAccess` — канал eDP AUX. Восстановлено из обёртки
(класс `IGCLAUXFunc`):

- поиск: `ctlEnumerateDisplayOutputs`, на каждом выходе native-AUX чтение DPCD `0x400` (Sink OUI),
  3 байта; Himax — `94 0B D5`;
- регистр контроллера (`HX8874RegRead`) — четыре операции I2C-over-AUX на адрес `0xF2`:
  запись `0D 00`, запись `20 01`, запись с флагом MOT 10 байт `00 <адрес LE, 4 байта> 00…`,
  чтение 4 байт. Регистры: `0xE7800210` ROM Ver, `…214` ROM Date, `…218` FW Ver, `…21C` FW Date;
- `ctl_aux_access_args_t` (0xB0): Size@0, OpType@8 (1 чтение, 2 запись), Flags@0xC (1 native,
  2 I2C, 4 I2C MOT), Address@0x10, DataSize@0x24, Data[132]@0x28.

Служба сравнивает с каталогом **ROM Ver** (его же утилита отдаёт кодом выхода): на TM2424
`0x570B06`, дата ROM `2026-03-18`; FW Ver `0x2701`. Каталог — `740B08`.

Ограничения экранного канала:

- **работает только пока встроенная панель активна** — локальный сеанс и включённый экран. По RDP
  IGCL отдаёт ноль выходов, и сама утилита Xiaomi пишет «No HX device». По её логам за
  июль–октябрь она не находила контроллер примерно в половине запусков (ночные сканы, удалённые
  сеансы). Значит, «версия неизвестна» — нормальное состояние, а не ошибка;
- чтение регистра включает **записи в контроллер** (`0D 00`, `20 01`, адрес). Это ровно то, что OEM
  делает при каждом скане, регистры прошивки не меняются, но это всё же запись в TCON — если делать
  в приложении, то только по кнопке проверки;
- живьём за ноутбуком нашим кодом **ещё не проверено**: и ресерч XIC-103, и реализация XIC-104 шли по
  RDP. По RDP проверено только «панели нет → версия неизвестна, ни одной AUX-операции» (в журнале
  `PanelFirmware: контроллер Himax не найден`). Сам алгоритм независимо подтвердил gxcreator в
  [issue #100](https://github.com/Oksion/XiControl/issues/100): своим скриптом за ноутбуком получил
  ROM Ver `0x570B06` и FW Ver `0x2701`, как в логе OEM-утилиты. Проба — `panel-fw-version.ps1` в рабочем каталоге
  проекта (вне git): без ключей только читает DPCD, с `-ReadVersion` повторяет последовательность OEM.

**Ревизии в синтетических id (`REV_1236/1237`, `REV_1836/1837`) расшифровать нельзя.** Служба
сопоставляет прошивку по коду модуля (`fw_id`) и версии, а hardware-id из каталога лишь пишет в лог
(«Firmware server hwid»). У обеих ревизий одного модуля версия одинаковая, пакет один. Привязать
ревизию к нашему железу нечем: у тачпада в системе `BLTP7853` без ревизии, у панели — OUI `94 0B D5`.

**Чего это не решает.** У экрана ROM Ver `57.0B.06`, в каталоге `74.0B.08`. Отличается старший
байт, и по одному номеру нельзя сказать, новее ли это прошивка для той же панели или пакет под
другой вариант панели в той же модели. У тачпада картина чище: `44.25` совпадает, отличается
последняя часть. Поэтому даже с чтением версии «у вас старее» честно говорить можно только про
тачпад; для экрана — показывать обе версии рядом, без вывода.

### Что внутри пакета тачпада (разбор 2026-10-20)

`P701_TouchPad_0728_01_351301.zip` (1 973 496 байт, md5 совпал с каталогом) скачан для разбора, ничего
не запускалось. Внутри:

- `TP\BL7853_V3.5.13.01_20260615(67D2).bin`, 64 КБ — прошивка **контроллера касаний Betterlife
  BL7853**. Код начинается с таблицы переходов `48 00 xx xx`, похоже на Andes NDS32; rizin эту
  архитектуру не знает, код не дизассемблирован;
- `Force\44.25.13.0.bin` (она же в корне), 33 КБ — прошивка **отдельного MCU силы и вибрации**,
  Cortex-M (векторы: SP `0x20003C60`, reset `0x0100108D`). HID-дескриптора в нём нет: это MCU за
  контроллером касаний, наружу он виден только через `COL05`. Утилита так и пишет: «current force
  version», «read force calibrate data»;
- `FirmwareTouchPadTool.exe` + `btl_upgrade.dll`/`btl_hid_transfer.dll` (BetterlifeForwardTool) —
  прошивальщик. Ходит в `col04` и `col05`, вызывает MIFS `MiInterface`, ищет окно
  `mi_touch_gesture`/`MiTouchGestureClass` (`FindWindowExW`) — по всей видимости, чтобы на время
  прошивки унять жесты PC Manager;
- `Install.bat` вызывает `FirmwareScreenTool.exe --update HX_V0057_0B06.bin` — команду прошивки
  **экрана**, которой в архиве нет: батник скопирован из пакета панели. Совпадение: `0057_0B06` — это
  ровно текущий ROM Ver нашей панели `570B06`;
- `CCP\ibtusb.*` — посторонний драйвер, к тачпаду отношения не имеет.

**Аппаратных «умных жестов» в прошивке нет.** В BL7853 два HID-дескриптора: обычный PTP и вариант с
силой — на TM2424 стоит второй. Он даёт только: мышь (ID 1, legacy-режим), PTP на 5 касаний с
16-битным Tip Pressure (ID 4), служебные feature-репорты (ID 2/3/5/6/7) и два вендорских канала по
32 байта — `0xFF00` (ID 14, `COL04`) и `0xFF01` (ID 13, `COL05`). Ни клавиатуры, ни Consumer Control,
ни usage жестов: распознанный жест прошивке передать в Windows просто нечем, кроме вендорских
каналов, а в `COL05` input-репорты — ответы на запросы. Значит, жесты Windows (2–4 пальца) считает
сама Windows по контактам, а краевые жесты и сильное нажатие Xiaomi — PC Manager (`PluginGesture.dll`)
по тем же контактам и давлению. На «железе» остаётся только тактильная часть: порог клика `0x5B` и
второй щелчок на сильном нажатии `0x59` прошивка отрабатывает сама, но событием наружу не сообщает.
Не проверено: шлёт ли прошивка что-то непрошенное в `COL04` (сам канал — команды контроллеру, им же
читается версия, см. выше) — для этого нужен код BL7853.

## 5. Где лежат данные

Захват не в репозитории (сырые ответы содержат хеш серийника машины) — он в рабочем каталоге
проекта, `ota-capture/`:

| Файл | Что это |
|---|---|
| `driver_cache.dat` | каталог от сервера, как его хранит служба: 1259 hwid / 18 пакетов |
| `ota_requests.jsonl` | 26 реальных запросов (тело до base64) |
| `ota_responses.jsonl` | 26 ответов на них |
| `scan_log_2026-10-10.txt` | срез лога службы за этот скан |
| `README.md` | тот же протокол кратко, рядом с данными |

Рядом же `ota-check.ps1` — рабочий скрипт-прототип (PowerShell 5.1 и 7, админ не нужен):

| Запуск | Что делает |
|---|---|
| `-Diag` | диагностика: как определилась модель, выведенная версия BIOS, запрос по 4 модулям + BIOS, сверка. Вывод можно целиком прислать разработчику — `sn` усечён |
| (без аргументов) | полная проверка: все 25 модулей + BIOS, сверка, ссылки на то, что новее |
| `-Offline` | без сети, сверка по `driver_cache.dat` (нужна установленная служба) |
| `-Module WLC,IGC` | опросить только эти модули |

**`-Diag` — штатный способ проверить другую модель:** человек с другим ноутбуком запускает его у
себя и присылает вывод. Самое интересное в нём — вывелась ли версия BIOS (правило «последние 4 hex»
снято с одной машины) и вернул ли сервер каталог для этого `product`.

## 6. Как снять заново

Если понадобится свежий каталог или проверка на другой модели:

1. Поставить Xiaomi PC Manager (китайский, при желании с англификатором — он только переводит UI).
2. Открыть «Управление драйверами» → «Проверить».
3. Забрать из `C:\ProgramData\MI\MiDeviceService\log\MiDeviceService_log.txt` строки
   `[OTA] Post json val =` (запрос) и `[OTA] Post response val =` (ответ).
4. PC Manager можно удалять: служба `MiService` остаётся и `driver_cache.dat` вместе с ней.

Подпись проверяется локально: взять `body` из лога, посчитать `MD5(appid+body+key)` и
сверить с `sign` того же запроса — так алгоритм и подтвердился.
